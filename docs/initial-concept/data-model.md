# Quire 初期データモデル

## 位置付け

この文書は初期構想段階のデータモデルを定義する。

実装開始前に、Quireが何を正本として扱い、何を再生成可能な補助情報として扱うかを明確にすることを目的とする。

名称は仮称を含む。UI上の呼称は後から変更してよい。

## 基本方針

Quireの正本は通常のファイルとディレクトリである。

本文や添付ファイルをQuire専用DBへ移さない。

Quire固有の情報は、次のどちらかに限定する。

- 文書から再生成可能なキャッシュやインデックス。
- Quire固有の設定、UI状態、履歴管理情報。

Quireを使わなくなった場合でも、主要データはそのまま利用できなければならない。

## Workspace

ObsidianのVaultに相当する作業単位を、初期設計では `Workspace` と呼ぶ。

名称は確定ではない。

Workspaceは一つの通常ディレクトリをルートとする。

例:

```text
notes/
├─ README.md
├─ daily/
│  └─ 2026-10-06.md
├─ projects/
│  └─ quire.md
├─ images/
│  └─ architecture.png
└─ .quire/
```

Workspace配下のファイルはExplorer、Git、Neovim、VS Code等から通常通り操作できる。

QuireはWorkspaceを所有しない。

QuireはWorkspaceを解釈し、編集し、索引化し、履歴管理する。

## Document

Quireが編集・表示対象として認識するファイルを `Document` と呼ぶ。

初期実装ではMarkdownを第一対象とする。

ただしデータモデル上はDocumentとMarkdownを同一視しない。

将来、プレーンテキストやその他のテキスト形式を扱える余地を残す。

Documentの識別にQuire専用UUIDを必須としない。

基本的にはWorkspaceからの相対パスを識別子として扱う。

例:

```text
projects/quire.md
```

ファイル移動・改名時のリンク追従など、パスだけでは不足する処理についてはインデックス側で補助情報を持ってよい。

## Asset

画像、PDF、圧縮ファイル、その他Documentから参照されるファイルを `Asset` と呼ぶ。

Assetも通常のファイルである。

Quire専用コンテナへ格納しない。

Assetの保存場所は固定しない。

Workspace設定として次の方式を選択可能にする余地を残す。

- Documentと同じディレクトリ。
- Workspace内の共通添付ディレクトリ。
- Documentごとの添付ディレクトリ。
- ユーザーが指定した相対パス。

初期実装では一つの単純な既定値を採用し、設定可能範囲は必要に応じて増やす。

## Link

Document内のリンクを解析し、インデックス上で関係として保持する。

リンクの記法と、解決されたリンク先を分離して扱う。

少なくとも次を区別する。

- 通常のMarkdownリンク。
- Wiki Link形式。
- Workspace内ファイルへの相対リンク。
- 見出しへのリンク。
- 外部URL。
- 解決できないリンク。

リンク情報はDocumentから再生成可能であり、正本ではない。

ファイル移動・改名時には、ユーザーが望む場合に参照元Documentを更新できるようにする。

勝手な大量書き換えは行わず、変更内容を確認・復元可能にする。

## Tag

タグはDocument本文または明示的なメタデータから抽出する。

タグ一覧そのものを独立した正本DBにはしない。

タグ索引は再生成可能とする。

対応する記法はMarkdown拡張仕様と合わせて別途定義する。

## Metadata

文書固有のメタデータは、可能な限り文書と一緒に保持できる形式を優先する。

MarkdownではYAML front matter等が候補になる。

Quireにしか意味がない一時的な状態をDocument本文へ書き込まない。

次を分離する。

### Portable metadata

文書と一緒に移動、同期、Git管理する価値がある情報。

例:

- タイトル。
- タグ。
- 作成者。
- 文書種別。
- ユーザーが明示した属性。

### Local state

そのPCまたはQuireの現在セッションだけに意味がある情報。

例:

- カーソル位置。
- スクロール位置。
- 一時的なペイン配置。
- 最近開いた文書。
- ウィンドウ位置。

Local stateを本文へ保存しない。

## .quire

Workspace固有のQuire情報が必要な場合、ルート直下の `.quire/` を使用する案を基本とする。

ただし全情報をここへ集約する必要はない。

初期案:

```text
.quire/
├─ workspace.toml
└─ README.md
```

`workspace.toml` はWorkspaceとともに共有する価値がある設定だけを保持する。

例:

- 添付ファイルの保存方針。
- 除外パターン。
- Markdown互換モード。
- Workspace固有の表示設定のうち共有すべきもの。

次のような再生成可能または端末固有の情報は、原則としてWorkspace内へ置かない。

- 全文検索インデックス。
- リンクグラフキャッシュ。
- WebViewキャッシュ。
- ブラウザCookie。
- ウィンドウ位置。
- 一時ファイル。

これらはOSのアプリケーションデータ領域へ保存する。

## Workspace ID

パスだけで端末固有状態を識別すると、Workspace移動時に状態が失われる。

一方、すべてのWorkspaceへ管理用IDファイルを書き込むことも避けたい。

初期実装では `.quire/workspace.toml` を持つWorkspaceについてはランダムなWorkspace IDを保持する案を採用する。

既存フォルダをQuireで一度開いただけの場合に、即座にファイルを書き込むかは別途決定する。

ユーザーのフォルダへ暗黙に管理ファイルを作成する挙動は、技術検証後に確定する。

## Application data

端末固有データはWindowsではユーザーのアプリケーションデータ領域へ保存する。

概念上は次のように分ける。

```text
Quire/
├─ settings/
├─ workspaces/
│  └─ <workspace-id>/
│     ├─ state/
│     ├─ index/
│     └─ cache/
└─ webview/
```

実際のパスはTauri等のOS標準APIから取得し、固定パスをコードへ埋め込まない。

## Index

検索、タグ、リンクグラフ等の高速化用データをIndexとして扱う。

Indexは常に再生成可能でなければならない。

Index破損によってDocumentが失われてはならない。

初期対象:

- ファイル一覧。
- ファイル名検索。
- Markdown本文全文検索。
- 見出し。
- タグ。
- 発リンク。
- バックリンク。
- 未解決リンク。

SQLite等を使用する場合でも、それは正本ではなくキャッシュである。

## 履歴

履歴のユーザー向け概念とGitの内部概念を分離する。

ユーザー向けには次の概念を提供する。

- Snapshot: ある時点のWorkspace状態。
- Change: Snapshot間の差分。
- Restore: 過去状態からファイルまたはWorkspaceを復元する操作。

初期実装ではGitを履歴エンジンの第一候補とする。

## Gitとの関係

### Quireが新規作成したWorkspace

Gitによる履歴管理をQuireが自動で初期化してよい。

ただし通常UIで `git init`、stage、commit等をユーザーへ要求しない。

### 既存Gitリポジトリ

既存リポジトリでは、Quireがユーザーの現在ブランチやindexを勝手に変更しないことを原則とする。

単純な自動 `git add -A && git commit` は採用しない。

Quireの自動Snapshotは、Gitの専用refや独立した一時index等を使い、通常のGit操作と分離する方式を技術検証する。

候補:

```text
refs/quire/history/<workspace-id>
```

この方式ではQuire用SnapshotをGit objectとして保存しつつ、ユーザーのbranch、HEAD、staging areaを変更しない。

既存リポジトリ内のサブディレクトリをWorkspaceにした場合を含め、具体的なtree生成方法は技術スパイクで検証する。

## 自動Snapshot

自動保存と履歴Snapshotを同一操作にしない。

ファイル保存は高頻度で行ってよい。

履歴Snapshotは意味のある単位へまとめる。

候補:

- 一定時間編集が止まった時。
- Quire終了時。
- 文書切り替え時。
- 明示的な「履歴へ保存」操作時。
- 大量変更の直前。

最終的な条件は実使用で調整する。

重要なのは履歴数を減らすことではなく、戻りたい状態を見つけやすくすることである。

## 外部変更

WorkspaceはQuire以外から変更されることを前提とする。

Quire起動中にExplorer、Git、Neovim等から変更されても破綻しない設計にする。

ファイル監視によって変更を検出し、Indexと表示を更新する。

編集中Documentと外部変更が競合した場合は、黙って上書きしない。

初期実装では少なくとも次を区別する。

- Quireに未保存変更がない場合: 外部変更を再読込可能。
- Quireに未保存変更がある場合: 競合として扱い、ユーザーへ選択肢を出す。

## 除外

次のファイルはWorkspaceに存在していても、既定では検索や履歴Snapshotから除外する候補とする。

- `.git/`。
- Quire自身の再生成可能キャッシュ。
- OSやエディタの一時ファイル。
- ユーザー指定の除外パターン。

`.gitignore` をそのままQuireの除外規則として使うかは確定しない。

Gitで無視したいものとQuireで検索したいものは一致しない可能性があるため、別概念として扱えるようにする。

## データ損失に関する原則

Quire内部の状態よりファイルを優先する。

不整合が起きた場合、Quire側のインデックスやキャッシュを捨てて再構築できる設計にする。

自動処理による削除、移動、リンク書き換え、履歴復元は、可能な限り直前状態へ戻せるようにする。

## 未確定事項

実装前後の技術スパイクと実使用で次を確定する。

- Workspaceの正式名称。
- `.quire/` をどの時点で作成するか。
- Workspace IDの生成条件。
- Gitが存在しない既存フォルダを開いた時、自動でGit管理を開始するか。
- 既存Gitリポジトリでの専用ref方式。
- Snapshotの生成タイミング。
- 添付ファイルの既定保存場所。
- Markdown front matterの標準方針。
