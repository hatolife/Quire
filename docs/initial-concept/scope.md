# Quire スコープ

## 目的

Quireが何を担当し、何を担当しないかを定義する。

Quireは多くの既存ツールと接続できるため、境界を定めなければエディタ、IDE、ブラウザ、ファイルマネージャ、Gitクライアントなどあらゆるソフトウェアの機能を取り込み得る。

機能の採否は「実装できるか」ではなく、「文書作業環境としてQuireが持つべき責務か」で判断する。

## Quireが扱う中心概念

Quireの中心は文書と、その文書を扱うための作業環境である。

基本的な対象は次とする。

- テキスト文書。
- Markdown文書。
- 画像。
- 文書から参照される添付ファイル。
- 文書を整理するディレクトリ。
- 文書間のリンク。
- タグやその他のメタデータ。
- 文書の変更履歴。
- 文書を探すためのインデックス。
- 文書作成時に参照する外部情報。
- 文書を扱うためのユーザー設定。

これらの集合をQuire上の一つの作業単位として扱う。

呼称と詳細なデータモデルは別途定義する。

## 本体で提供する機能

### 文書操作

以下はQuire本体の責務とする。

- 文書の新規作成。
- 文書を開く。
- 文書を編集する。
- 文書を保存する。
- 文書を削除する。
- 文書を移動する。
- 文書名を変更する。
- ディレクトリを作成、移動、削除する。
- 画像やその他ファイルを追加する。
- 文書内から添付ファイルを参照する。
- 複数文書を一つの作業環境で扱う。

通常のファイルシステム操作との互換性を維持する。

### 編集

単純なテキスト入力だけではなく、本格的な編集環境を提供する。

最低限、次を実現可能な構成とする。

- 一般的なGUIエディタとしての編集。
- Undo / Redo。
- 検索、置換。
- 複数カーソル等の高度な編集機能。
- キーボード中心の操作。
- Neovim相当の編集環境。
- ユーザー定義のキーマップ。
- 必要に応じた外部編集機構との統合。

Neovimを採用する場合も、通常利用時にNeovimの存在を意識する必要はない状態を目指す。

### Markdown表示

MarkdownをQuireの主要な文書形式として扱う。

以下を本体で扱う。

- Markdownの表示。
- 編集内容のプレビュー。
- 文書内リンク。
- 画像。
- 表。
- コードブロック。
- 数式等、文書用途として一般的な拡張。
- Obsidianで広く利用される記法のうち必要なもの。

Obsidian独自記法を無条件ですべて再現することは目的としない。

利用価値と既存データとの互換性を考慮して個別に採否を判断する。

### 文書間リンク

文書同士の関係を本体で管理できるようにする。

少なくとも次を対象とする。

- 文書へのリンク。
- バックリンク。
- 未解決リンク。
- リンク先の変更への追従。
- リンクされた文書の検索。
- 文書間関係の可視化。

グラフ表示そのものより、文書間の関係情報を正しく管理することを優先する。

### 検索

文書を探す機能は本体機能とする。

少なくとも次を対象とする。

- ファイル名検索。
- 文書全文検索。
- タグ検索。
- リンク関係による検索。
- 絞り込み。
- 検索結果から文書への移動。

検索のためにユーザーが外部ツールを別途構築する必要がない状態を目指す。

### 履歴管理

文書の変更履歴を本体機能として提供する。

内部実装としてGitを利用することを有力候補とする。

通常ユーザー向けにはGitの概念を必須にしない。

Quire上では例えば次の操作として提供する。

- 過去の状態を見る。
- 変更内容を見る。
- 以前の状態へ戻す。
- 削除した文書を復元する。
- 任意時点の状態を保存する。

高度なユーザーが通常のGitツールから同じデータを操作できることを妨げない。

Gitブランチ、rebase、cherry-pickなどGit固有の高度な操作を、すべてQuireのGUIで再実装することは初期の責務としない。

### レイアウト

複数の情報を同時に扱える画面構成を本体機能とする。

例として次を扱う。

- 文書一覧。
- エディタ。
- プレビュー。
- 検索結果。
- バックリンク。
- Webページ。
- その他補助パネル。

ペインを分割し、ユーザーが配置を変更できることを想定する。

特定の固定レイアウトだけに依存しない。

### Web参照

文書作成中にWeb上の情報を参照する行為をQuireの作業範囲に含める。

そのため、アプリ内でWebページを開く機能を持つ。

ただしQuire自身がWebブラウザ製品になることは目的としない。

本格的なブラウザエンジンを独自開発しない。

既存のWebViewまたはブラウザエンジンを利用する。

必要性が確認できる場合、ブラウザ拡張、ユーザースクリプト、認証状態などについても検討する。

### 設定とカスタマイズ

次を本体で扱う。

- UI設定。
- キーバインド。
- エディタ設定。
- Markdown表示設定。
- レイアウト。
- テーマ。
- 外部ツール連携。
- 保存や履歴管理の動作。

設定可能にすること自体を目的にしない。

安全かつ妥当な既定値を用意し、設定しなくても利用可能にする。

## 拡張機構が担当するもの

本体の目的に直接必要でない特殊用途は拡張機構で扱ってよい。

例:

- 特定Webサービスとの連携。
- 特定業界専用の文書形式。
- 特殊な可視化。
- 特定ユーザーだけが必要とするワークフロー。
- 独自のコマンド。
- 独自パネル。
- 独自レンダラー。
- 独自インポーター、エクスポーター。

ただし、多数のユーザーが基本用途で必要とする機能が拡張側に集中した場合は、本体機能への昇格を検討する。

## Quireが当面やらないこと

### IDEそのものにはならない

ソースコードを文書として開いたり、NeovimやLSPを利用したりすることは妨げない。

しかしVisual Studio、VS Code、JetBrains IDE等を置き換える完全なソフトウェア開発IDEを作ることは目的としない。

プロジェクトビルド、デバッガ、プロファイラ等は初期の本体責務に含めない。

### Gitクライアントそのものにはならない

履歴管理のためにGitを利用する。

しかしGitのすべての操作をGUI化することを目的としない。

高度なGit操作が必要なユーザーは通常のGit CLIやGitクライアントを利用できる。

### Webブラウザそのものにはならない

Webページの閲覧は文書作業を補助する機能として提供する。

タブブラウザ市場でChrome、Firefox、Edge等と競争することは目的としない。

ブラウザエンジンそのものは開発しない。

### ファイルマネージャそのものにはならない

Quireが管理する文書群のファイル操作は提供する。

しかしOS全体を管理するExplorer代替を作ることは目的としない。

### クラウドサービスを必須にしない

アカウント登録、Quire専用サーバー、月額サービス等を主要機能の利用条件にしない。

将来公式同期サービスなどを提供するとしても、ローカル利用を妨げない。

### 独自文書形式へ囲い込まない

主要文書をQuireでしか読み書きできない形式へ移行させない。

独自形式が必要な場合は、補助情報や交換可能なデータに限定することを原則とする。

## 判断が必要な領域

以下はQuireとの親和性が高い一方、範囲が急激に拡大し得るため、個別に採否を判断する。

- PDF閲覧、注釈。
- Office文書閲覧。
- 電子書籍。
- RSS。
- Webクリップ。
- 文献管理。
- タスク管理。
- カレンダー。
- ホワイトボード。
- Canvas型UI。
- データベース型ノート。
- AI支援。
- 複数端末同期。
- 共同編集。
- Web公開。
- モバイル版。

これらは「便利だから」ではなく、Quire上の文書作業をどの程度自然に改善するかを基準に判断する。

## 機能採否の基準

新しい機能を本体へ追加するときは、少なくとも次を確認する。

1. 文書を作る、読む、整理する、探す、参照する、履歴を管理する、のいずれかを直接改善するか。
2. 多くのユーザーが同じ問題を個別に外部ツールで解決する必要があるか。
3. Quire本体へ統合することで明確に操作が簡単になるか。
4. 通常のファイルや既存ツールとの互換性を損なわないか。
5. 実装と保守の複雑さに対して十分な価値があるか。
6. 本体ではなく拡張機能として実装する方が自然ではないか。

1から3のいずれにも強く該当しない機能は、本体へ追加しないことを基本とする。

## 初期到達点

最初の実用版では、少なくとも次の一連の作業がQuireだけで成立することを目指す。

1. 文書群を開く、または新しく作成する。
2. 文書一覧から目的の文書を探す。
3. 文書を編集する。
4. Markdownとして表示を確認する。
5. 画像やファイルを追加する。
6. 文書同士をリンクする。
7. 全文検索する。
8. Web上の資料を横に表示して参照する。
9. 変更履歴を見る。
10. 必要なら以前の状態へ戻す。
11. Quireを閉じる。
12. 同じファイル群を他の一般的なツールからも利用できる。

この一連の操作にGit、Neovim、インデックス生成などの手作業を要求しないことを、最初の完成条件とする。
